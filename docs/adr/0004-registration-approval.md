# ADR-0004：用户注册管理员审批机制

## 状态

Accepted

## 日期

2026-08-04

## 背景

ToolHub 主要部署于企业内网与私有私有云环境，作为内部工具平台与资产核对系统。随着接入部门增多，需要建立严密的准入控制（Access Control）。

在既有实现中，系统缺乏统一的外部 SSO 基础设施，且“首用户自动注册为超级管理员”逻辑（`count == 0` 或 `count == 1` 分支）存在严重的安全漏洞：
1. **删光用户后竞态漏洞**：若系统中所有用户被管理员清理删除，下一个任意注册者将自动触发逻辑成为超级管理员；
2. **并发注册竞态漏洞**：在无用户状态下，多个并发注册请求同时判断数据库 `count == 0`，可能同时拿到超级管理员权限。

同时，依靠“管理员手动建号”运维成本高且初始密码分发存在安全隐患；而直接接入企业 SSO 存在基础设施依赖重、私有部署环境差异大等问题。因此，系统需要一种长期的、自包含的准入控制机制：**开放注册 + 管理员审批**。

## 决策

为实现长效、安全的企业内网准入控制，定稿以下设计决策：

### 1. 动机与准入控制方案

采用 **开放注册 + 管理员审批** 方案，取代“管理员手动建号”与“外部 SSO 绑定”：
- **拒绝“管理员建号”**：手动建号增加系统管理员日常运维负担，且初始密码的分发过程（明文传输、口头告知）存在泄露风险。
- **拒绝“SSO 接入”**：私有部署环境中客户的 IDP（如 OIDC/SAML/LDAP）环境极其复杂甚至缺失，作为 long-term 基础架构，系统必须具备自包含的准入治理能力。
- **采用“开放注册 + 管理员审批”**：由用户自主填写凭据，管理员在控制台集中审核，兼顾安全准入与自治便捷性。

### 2. 状态模型 (Status Model)

在 `User` 模型中新增 `status` 枚举类型，明确用户生命周期状态：
- **`pending`**：待审批（新注册默认状态）；
- **`approved`**：已通过（正常可用状态）；
- **`rejected`**：已拒绝（审批未通过）。

**`is_active` 字段**：保留原语义（用于账号在已被通过后，后续因离职或安全原因被管理员手动“停用/启用”禁用操作）。

**存量用户处理**：数据库迁移脚本将所有存量用户的 `status` 回填为 `approved`，确保系统平滑升级，不影响现有已注册用户的正常使用。

### 3. 注册流程与防线调整

- **注册凭据**：注册仅需 `username` 与 `password`。
- **审批防线**：注册完成后用户状态即为 `pending`，**不分配任何业务角色**（天然零角色零权限）。
- **角色补齐**：审批通过时（Approve），管理员可指定分配角色；若未指定（Body 留空），默认分配 `"工具使用者"`（Tool User）角色。
- **移除首用户超管逻辑**：完全删除代码库中原有“首用户注册自动成为超级管理员”（`count == 0` 或 `count == 1`）的分支逻辑，彻底消除删光用户后下一注册者变超管及并发注册夺权两个安全漏洞。

### 4. 首个管理员 Bootstrap

为了在无“首用户自动超管”逻辑后完成系统的初始化，采用部署期配置方案：
- **配置项**：通过环境变量或 CLI 配置初始超级管理员凭据（`INITIAL_ADMIN_USERNAME` / `INITIAL_ADMIN_PASSWORD`）。
- **初始化逻辑**：系统启动时检查用户表，若用户表为空且已配置上述环境变量，则自动创建状态为 `approved` 且具备超级管理员角色的初始账号。
- **软失败（Soft Failure）设计**：若用户表为空且未配置环境变量，系统**不得拒绝启动**。拒绝启动会导致自动化部署、CI/CD 流程或容器编排中因为缺少初始化凭据而触发“鸡生蛋”死锁。处理方式为：打印错误日志（ERROR Log）并在健康检查端点（Health Check）中标记为失败/警告（软失败）。

### 5. 审批端点与权限控制

- **API 端点**：
  - `POST /admin/users/{id}/approve`：通过审批。Body 中的 `role_ids` 为可选参数，留空时默认分配 `"工具使用者"` 角色。
  - `POST /admin/users/{id}/reject`：拒绝审批。
- **权限设计**：沿用既有的 `user:write` 权限点，**不新增专用权限**。此举可避开种子数据（Seed Data）幂等更新时跳过存量数据库导致旧库丢失新权限的兼容性坑。
- **审计日志**：所有审批动作必须通过 `log_action` 记录审计事件（`user.approve` 与 `user.reject`）。
- **层级保护**：严格沿用既有的层级保护语义（低阶管理员不得对同阶或高阶管理员执行审批/提权/修改操作）。

### 6. TTL 清理与拒绝可逆机制

- **TTL 自动清理**：处于 `pending` 或 `rejected` 状态的用户，自 `created_at` 创建时间起算，达到 `REGISTRATION_PENDING_TTL_DAYS`（默认 7 天，环境变量可配置）后，由后台任务自动执行物理删除（Physical Delete）。
- **会话吊销 (Session Revocation)**：物理删除执行前，必须先调用会话吊销逻辑：递增用户的 `token_version` 并定向推送 `session.revoked` WebSocket 事件（遵循 [ADR-0002](./0002-session-token-version-and-permission-events.md)），清除可能残留的在线会话。
- **业界对照与组合设计**：
  - *OpenProject*：邀请 Token 7 天过期但不删号；
  - *Nextcloud*：占位记录 30 天清理；
  - *Keycloak*：自动删号属于长期未实现的 RFE (#38108)。
  - **ToolHub 方案**：“**删除兜底 + 拒绝可逆**”组合。管理员可以通过 `POST /admin/users/{id}/approve` 将处于 `rejected` 状态的用户重新恢复为 `approved`（拒绝操作可逆）；而 7 天 TTL 清理退化为未处理垃圾数据的超时物理删除兜底机制。

### 7. 登录语义与 Realtime Notification

- **`pending` 状态登录**：允许登录。登录后重定向至“待审批”专属页面。由于该状态下天然未分配任何角色（零权限），后端的接口权限守卫与前端的路由守卫会自动限制其访问所有业务功能。
- **`rejected` 状态登录**：直接返回 **HTTP 401**，响应文案明确区分并提示“账号审批未通过/已拒绝”（接受私有内网环境下的用户名枚举 Trade-off，以提升用户体验）。
- **TTL 过期删除后登录**：提示常规的“用户名或密码错误”（文案不区分未注册还是已删除）。
- **通知推送机制**：在无默认 SMTP 邮件基础设施的私有内网下，结果通知依赖 **Realtime Notification**（实时通知，遵循 [ADR-0001](./0001-realtime-websocket-notifications.md) 与 [ADR-0002](./0002-session-token-version-and-permission-events.md)）：
  - **用户侧**：实时长连接定向推送 `user.status.updated` 事件，提示客户端刷新状态；用户亦可随时登录系统查看待审进度。
  - **管理员侧**：新用户注册触发 `user.pending` WS 广播事件，管理员控制台侧边栏待审批菜单项实时更新计数徽标（Badge Counter）。
  - **未来扩展**：若后续引入 SMTP 邮件基础设施，审批结果邮件通知将被列为最高优先级补齐事项。

### 8. 防滥用策略 (Anti-Abuse)

- **注册限流**：针对注册接口启用基于 IP 地址的速率限制（Rate Limiting）。
- **域名白名单**：支持配置可选的注册邮箱/用户名域名白名单及后缀限制（Domain/Suffix Whitelist）。

### 9. 前端架构与组件移植

- **组件移植**：组件级移植 `satnaing/shadcn-admin`（MIT 许可证）的 `features/users` 与 `data-table` 基座，引入 `shadcn/ui` + `@tanstack/react-table`，全面替换现有的自研 DataTable/Modal。
- **交互规范**：
  - 实现服务端分页（Server-side Pagination）；
  - 状态筛选同步写入 URL 查询参数（URL-driven filtering state）；
  - 采用待审批/已通过/已拒绝 三态徽标（Tri-state status badge）。
- **拒绝整体 Admin 框架**：评估并否决引入 `react-admin` 或 `refine` 等整体框架，原因在于其实时层（Realtime layer）存在商业付费墙、设计语言与现有的 Tailwind/shadcn 系统冲突、且接口契约与 REST/WS 架构不匹配。

## 备选方案

| 方案 | 说明 | 结论 |
|------|------|------|
| **管理员手动建号** | 由管理员在控制台统一创建账号并分发初始密码 | **拒绝**：运维成本高，初始密码明文分发存在安全隐患。 |
| **强制外部 SSO 对接** | 依赖外部 OIDC / SAML / LDAP 进行身份认证 | **拒绝**：企业私有部署环境差异大，系统需具备自包含准入能力。 |
| **拒绝状态为不可逆终态** | 一旦拒绝直接物理删除或不可恢复 | **拒绝**：误操作容错率低；采用“拒绝可逆 + 7 天 TTL 物理删除兜底”更符合运营习惯。 |
| **引入整体 Admin 框架 (react-admin / refine)** | 使用开箱即用的 Admin 框架搭建用户管理页 | **拒绝**：实时推送层存在付费墙、与既有 shadcn/ui 设计风格冲突、API/WS 契约不匹配。 |

## 后果与影响

### 1. 权衡记录 (Trade-offs)
- **拒绝状态可逆**：将拒绝定义为可逆状态而非终态，允许管理员在 7 天 TTL 周期内重新 Approve，提升误操作容错率；延长了记录在数据库中的生命周期。
- **TTL 删除与审计日志**：物理删除 `pending`/`rejected` 用户可能导致审计日志（`audit_logs`）中出现孤儿外键引用风险。审计日志实现必须采用 `user_id` / `username` 文本快照存储，不得建立硬性数据库外键约束。
- **`pending` 允许登录**：允许待审批用户登录并访问待审页是业界较少见的取舍（降低对管理员邮件/线下通知的依赖，配合待审页与 WS 实时推送提供反馈）。
- **运营节奏假设**：7 天 TTL 基于企业内部管理员每周至少处理一次审批的运营节奏假设。

### 2. 测试策略 (Test Strategy)
认证与用户管理测试组必须包含以下场景校验：
- **状态转移测试**：验证 `pending` -> `approved`、`pending` -> `rejected` 以及 `rejected` -> `approved` 的状态流转与角色分配。
- **TTL 自动清理与会话吊销**：验证超时记录的物理删除，以及删除前 `token_version` 递增与 `session.revoked` 事件的触发（[Session Revocation](../../CONTEXT.md)）。
- **登录反馈测试**：验证 `pending` 状态登录成功但零权限、`rejected` 状态返回 401 专属文案、已删除账号返回 401 通用文案（“用户名或密码错误”）。
- **Initial Admin Bootstrap 软失败**：验证无用户且无环境变量配置时，应用启动正常（不崩溃/拒绝启动）、健康检查返回失败/警告，且后续不会因任何注册触发自动提权。
